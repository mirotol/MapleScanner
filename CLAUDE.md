# MapleScanner

Windows app that shows MapleStory Classic Free Market prices by reading the game window. Every player's scans go to one shared price database on Cloudflare, and every player gets prices from it.

## Rules

- **Read only the screen.** Everything live comes from the picture of the game window. Never read the game's network connections or ports, packets, memory or files, even when another tool does. If something isn't on screen, show a hint asking the user to open the window that displays it.
- **Reference data only supports what the screen shows.** `osms-items.json` can correct or complete a name read from the screen, and check that a tooltip was read in full. It never supplies a player's price, room, channel or seller, or adds a listing that wasn't read.
- **NPC prices come only from OSMS.** What an NPC pays is a fixed game value, so `osms-items.json` overrides the screen and the screen isn't read for it. What an NPC charges isn't in OSMS (NPC shops aren't in the client), so we don't show it.
- **Unknown is better than wrong.** Leave a value empty or the row as "hover to check" rather than guess. A wrong room or tier sends the player to the wrong place.
- **High prices are real.** Troll prices like 9,999,999 are real listings: keep them and show them in the range. Never remove an outlier, and never use an average.
- **Prices have to be hard to fake.** Each seller gets one vote: their newest ask and the middle of their sales. The usual price is the middle of sold prices, once 5 sellers have sold over 2 different days (3 until Nov 10), otherwise the lower quartile of asks, because a fake high ask is free but anyone can buy a fake low one. A deal is 10% under the usual price from 50K, and 20% under below that, because 10% of a cheap item is a few hundred mesos (measured on the real list, Nov 9). It must also be at or below the cheapest other ask. The rules live in `market.js`, with each attack as a test.
- **Gear verdicts need stats.** A name mixes clean and scrolled copies (`Emerald Earrings`: 20K and 900K), so on the stall card gear gets no percentage until a hover has read its stats. The Prices list does show one usual price per gear name, from every copy, and its card says "every condition" until its Stats filter (clean only, a range per stat) narrows the copies. Unread copies are left out while the filter is on, and a "check item" warning on gear needs it on.
- **Don't tell players what to list at.** Show sold prices and the cheapest ask, because a single number from the tool would become the market's price.
- **Players can't edit the data.** The app is for real players, not only its author (Nov 10), so nothing in it renames, moves or deletes items or listings, or sets a price by hand. The server has no endpoint for it. Every price comes from listings read off the screen, which is also the only shape that can be shared later. A wrong read is fixed in the reading code, not by hand.
- **No listing data on players' PCs** (decided Nov 10). Scans go to the shared database (a Worker and D1 in `cloud/`), and the app holds the last 14 days of listings in memory only (`cloud.js`). What stays on the PC is settings, the anonymous install key and icons. Without internet there are no fresh prices, and scans wait in memory until the server is back, lost if the app closes first. The stall card's bar says so.
- **Uploading is on by default and can be turned off, and every upload is traceable.** Since Nov 11 the player chooses (`shareScans`, see Settings), because SignPath's free code signing requires that sending data can be turned off during install. Off, nothing goes out and prices still sync. Each install that shares sends an anonymous key (`install.json`, made the first time a scan is sent). The Worker keeps only its SHA-256, never an IP address, and records in `reports` which installs saw each listing, so one install's data can be removed. Until `market.js` counts installs as well as sellers, a faker can invent sellers, so that must come before the public release.
- **Only the admin edits data**, through `/v1/admin/*` with the Worker secret `ADMIN_TOKEN` (`tools/admin.js`): move an item, delete a listing or item, block an install. The local Worker's token is in `cloud/.dev.vars`, which git ignores.
- **Game pictures stay on this computer.** Screenshots (`test/*.webp`, `*.jpg`, `*.png`, `design/shots/`), recordings in `debug/` and downloaded item icons are never committed or pushed to GitHub (decided Nov 10). `npm test` loads none of them, so it can run in CI. A test that needs a screenshot must skip when the file is missing, and checks on screenshots in a browser page are done locally.
- **MaplePrice (cozy-markets-dev/fm-overlay) has no licence.** Learn from its ideas, but don't copy its code or assets. Don't use its server or tokens.
- **MeowDB needs permission** for crawling, its API or its data files. See https://meowdb.com/reuse
- **OSMS Data Explorer is CC BY 4.0.** Keep its credit on the app's About tab (moved there from the Scanner tab's footer on Nov 10, at the user's request). Game content such as names and images is © Nexon and isn't covered, so don't bundle its icons without asking. The app downloads each icon once instead, see below.

## Commands

```bash
npm start
npm test
npm run dist
node serve.js
npm run items
```

- `npm start`: run the app from source
- `npm test`: price, name, tooltip card, Worker (`test/cloud.test.js`, over the D1 shim `test/d1-shim.js`) app-to-Worker (`test/cloud-client.test.js`) and website icon (`test/site.test.js`) tests
- `npm run dist`: build the installer `dist/MapleScanner-Setup-<version>.exe` locally, without publishing. Fails to replace `dist/win-unpacked` while that copy is running, so ask the user to close it first
- Releasing (since Nov 10): raise `version` in `package.json`, commit, tag `v<version>` and push the tag. `.github/workflows/release.yml` checks the tag matches, runs the tests, builds the installer and uploads it to a **draft** GitHub release. Players only get it once the draft is published on GitHub (only published releases are seen by the updater). Installed copies check at start and every 6 hours (`setupUpdates` in `desktop/main.js`, through `electron-updater`). With the `autoUpdate` setting on (default) a new version downloads in the background, off the About tab offers a Download button. A downloaded version installs on Restart now (`quitAndInstall`, silent, starts again) or when the app is closed. The page gets each step as an `update` message: the About tab says where it is, and the tab bar's end shows the download's progress, then an orange Restart to update. The stall card shows none of it. 0.1.0 and 0.2.0 only update silently on close; the About tab and its notices start with 0.2.1. Tested Nov 10 on the user's PC: 0.1.0 updated itself to 0.2.0, and 0.2.1 to 0.2.2 with the download notice and Restart now. `.github/workflows/test.yml` runs `npm test` on every push to `main`. Never change `build.appId` (`io.github.mirotol.maplescanner`): Windows knows the installed app by it, so a new one breaks updates. The old portable `MapleScanner.exe` can't update itself; players on it install once. Releases are unsigned until code signing is set up, so Windows warns on install.
- Code signing (set up Nov 11, not yet live): SignPath Foundation, free for open source, chosen over Certum (shows the author's legal name) and Azure Artifact Signing (US and Canada individuals only). The publisher players see is "SignPath Foundation". Its terms are why sharing can be turned off in the installer, and they need the code signing policy (`site/code-signing.html` at `/code-signing`, linked from every site page's footer, the front page too, plus the README section and each release's notes), two-factor login on GitHub and SignPath, builds on GitHub's own machines only, and an approver approving each signing request. `release.yml` signs only once the repository variable `SIGNPATH_ORGANIZATION_ID` and the secret `SIGNPATH_API_TOKEN` are set, and builds unsigned until then. Signed, it builds in two parts: `electron-builder --win dir`, sign `MapleScanner.exe` (SignPath artifact configuration `app`), `--prepackaged` to build the installer around it, sign that (`installer`), then `tools/refresh-update-info.js` makes `latest.yml`'s checksum and the blockmap again from the signed file, or the updater would refuse it. So each release is two requests to approve in SignPath. The configurations are kept in `signpath/` and pasted into SignPath, project `MapleScanner`, policy `release-signing`. They restrict product name and version, which needs `win.signAndEditExecutable` on (off until Nov 11). `electron-updater` only checks an update's signature when the build has `win.publisherName`, which electron-builder fills in only when it signs, so these builds don't check. Setting it (`["SignPath Foundation"]`) once signed releases are out would make updates refuse anything unsigned or signed by someone else, so only do that after signing works, and list every name if the publisher ever changes
- `npm run items`: refresh `osms-items.json` from OSMS Data Explorer, only if it has changed. The app never goes online for this. A Cash Shop `price` is in NX, so prices only come from `items.json`
- `node serve.js`: browser version on http://localhost:8123 (Edge or Chrome only, Firefox isn't supported). Prices come from `CLOUD_URL`, or else `PRODUCTION_URL` in `cloud.js`, the live Worker at https://api.maplescanner.app (deployed Nov 10, D1 `maplescanner` in Western Europe). The Worker only answers on that domain: its workers.dev address is off, because the account's subdomain is named after the author's email. Settings, its install key and icons go in `DATA`, default `data/`
- `npm run cloud:dev`: the Worker with a local D1 on http://127.0.0.1:8787, no Cloudflare account needed. Apply the schema first with `npx wrangler d1 migrations apply maplescanner --local --config cloud/wrangler.jsonc` (add `--persist-to <dir>` to both to keep a scratch copy apart). Then `CLOUD_URL=http://127.0.0.1:8787 node serve.js`. Two servers with different `DATA` folders act as two players (`app-a` and `app-b` in `.claude/launch.json`)
- `npm run cloud:deploy`: deploy the Worker. Needs `npx wrangler login`, the real `database_id` in `cloud/wrangler.jsonc` and `ADMIN_TOKEN` set with `wrangler secret put`. A new schema change is a new file in `cloud/migrations/`, applied with `wrangler d1 migrations apply maplescanner --remote`
- `npm run site:dev`: builds the website into `site/dist` and serves it on http://127.0.0.1:8790 (`site` in `.claude/launch.json`, which doesn't build, so run `npm run site:build` first). Opened from this computer it reads prices from the local Worker on 8787, never the real one, so start that too (`cloud-mock` serves the made-up market in `design/mock/worker`). `wrangler dev` let the browser keep old copies of rebuilt files (Nov 10): reload with the cache off before judging a change
- `npm run site:deploy`: builds and deploys the website to maplescanner.app as the Worker `maplescanner-site`. Deployed Nov 10 at the user's request, before the anti-fake rules, which are still to come. `www.maplescanner.app` isn't set up
- `tools/import-local.js`: sends an old `prices.db` (from before Nov 10) to the shared database with its dates, through `/v1/admin/import`. `tools/admin.js`: the admin's fixes

## Layout

- `desktop/`: Electron main process and preload. Starts the server and owns window capture and the pop-out window
- `serve.js`: local server for the pages and API, used by both the app and the browser version. It also serves item icons at `/icon/<id>.png`. `/api/state` (asked after every scan) is answered from memory, `?full` adds every item ever listed for the Prices list, `/api/history` asks the Worker, `/api/sightings` queues scans and `/api/status` says whether the price server is reachable
- `cloud.js`: the app's link to the shared database: recent listings in memory, synced every 30 s by cursor (`/v1/sync`), and an upload queue sent every 5 s. The stall card reads the open shop several times a second, so a listing is only sent again when a read adds something (channel, title, stats) or after 10 minutes
- `listing.js`: the checks a listing must pass (a real item under the list's spelling, sensible numbers, stats that fit, a scan time near now), shared by the Worker, which has the final word, and the app
- `cloud/`: the Worker (`index.js` entry, everything in `api.js` so Node can test it) and D1's schema in `migrations/`. Tables: `items` (counters kept by triggers), `listings` (raw listings, never calculated prices, one per seller, amount, price and sold state, with the old merge rule: most copies, widest dates, newest place, title and stats read), `uploaders`, `reports` and `removed` (tombstones, so apps drop what the admin removed). Listing ids never repeat (`AUTOINCREMENT`), so a tombstone can't hide a newer listing. Only items named in `osms-items.json` are kept: a read that isn't a real item is left out, and the stall card shows that row as `check`. A misread that matches another real item stays there until the admin moves it

- `site/`: the website for maplescanner.app (built Nov 10). Its header has Prices, Download and About (Nov 10: a GitHub link there looked out of place, so the source link is on About). The front page is Prices (the user's choice, Nov 10). `download.html` (`/download`) is the Download page: what the app does, a Download button that asks GitHub for the newest published installer (and stays a link to the releases page if that fails), how it works and installing. `about.html` has what the app reads, what it sends, the source code and every licence and credit, like the app's About tab. Its picture is the stall card drawn in HTML with `theme.css` and a made-up shop, because game pictures are never published. The front page is the app's own Prices page: `build.js` copies `prices.html` (as the site's `index.html`), `prices.js`, `pricing.js`, `market.js`, `theme.css`, the fonts and `osms-items.json` into `site/dist` and adds the site's header and `site.js`, and fails if a line it replaces is gone. `site.js` replaces the page's `api` and answers `/api/state` and `/api/history` in the browser from the Worker's public reads (`/v1/sync`, `/v1/items`, `/v1/history`), using `marketState` in `pricing.js`, the same code `cloud.js` builds the app's state with. It sets `PUBLIC_SITE`, which only changes wording where the app's says "you". Item icons (the user's choice, Nov 10, so visitors don't flood OSMS): `/icon/<id>.png` is the one address that runs code (`worker.js`, `run_worker_first`). `icons.js` downloads an icon from OSMS the first time anyone asks for it and keeps it in the R2 bucket `maplescanner-icons` under the game data's build, so OSMS gets one download per item, and only ids in `osms-items.json` are fetched. Tested in `test/site.test.js`. So the site does serve © Nexon icons from its own domain, though they're still never in the repo or the installer. Seller names and shop titles are shown as in the app (the user's choice, Nov 10), to be looked at again with the anti-fake rules, because they're words an install could make up. The site only reads: no install key, no uploads. A card's address is a link to it (`/?item=Iron Ore`), in the app's frame too. Every visitor downloads the last 14 days of listings, uncached, which is fine while the database is small and needs a cached read in the Worker before it's busy

- `scanner.js`: finds shops, tooltips, the minimap and the Change Channel window in a frame, and reads them
- `osms-items.json`: real item names, including Cash Shop items, plus NPC prices, scroll rates, gear slots, main stat lines, a plain copy's stats, which gear has no description, which items recharge and each name's item id for its icon, generated by `tools/update-items.js`. Don't edit it by hand
- `market.js`: listings to a market summary to a verdict. Pure, shared by the pages, and the only place price decisions are made
- `pricing.js`: name matching, map parsing, item facts and tooltip stats, shared by the pages and the server. Keep logic in these two when it can be tested in Node
- `app.js`: capture loop, merging scans into a shop, the stall card and tabs. It renders verdicts and doesn't decide them
- `prices.html`, `prices.js`: the shared price database, shown in a frame by the Prices tab so scanning carries on. One list of items, each with its kind under its name, as mesos.watch and meso.watch show it (search, the game's inventory tabs from `itemFacts().kind`, sorted by clicking a column header, again to turn it round), and clicking one opens a card over it: usual price, cheapest ask in the time picked (1h to All, opening on 24 h), last sale, a chart, every listing, and the Stats filter for gear. It only reads: nothing on it changes the data. Shops close, so "now" is whatever time chip the player picks rather than a fixed cut-off. An ask the same seller was later seen selling at that price is gone (`soldSince` in `market.js`), so the card lists it once, as its sale, under Sold and Both, never Asking. Before (Nov 10), Leather's Asking list began at 125 and 130, both sold, under a cheapest ask of 205. Nothing in the game links an ask to its sale, so only what's sure ties them, because hiding an ask that's still up is worse: a named seller (an unknown one could be any shop), the same amount (50 for 6,500 selling doesn't end 100 for 13,000), and as many copies sold as were up (1 of 3 identical rows leaves 2). `/api/state` sends each listing's `qty` and `copies` for this. Two listings are one seller's (`sameSeller` in `market.js`) when the name is the same, or close (OCR reads one name two ways, Loodles and Lood1es) and on the same stall: the same shop title, or the same channel and room. Before (Nov 10), any two names 80% alike were one seller, so Ludilove2's newer ask hid Ludilove's cheaper one. The stall card passes its own shop (`thisShop` in `app.js`), so the seller being judged is still left out under a misread name. The chart (Nov 10) has two views, kept while moving between items. Dots is every listing. Its scale (`chartRange` in `pricing.js`) fits the prices instead of starting at zero, from a third of the lower quarter up to 4× the usual price, and anything past that is a ▲ or ▼ on the edge, with the furthest named in the legend: before, two troll asks among three set the scale to 2M over asks of 77, and Power Elixir's 4,200 to 6,500 sat on 0 to 10K. A busy item's dots are smaller and see-through. Time marks (`timeTicks`) count back in round hours up to a day and a half, then mark midnights by date (`9 Nov`), weekly on Mondays for long spans. Trend is what sold (middle of sales) and what was asked (lower quarter) each day, over the 3 days to it, from `dailyPrices` in `market.js`, with no point for a day under 5 named sellers. Straight lines, broken over gaps of more than 3 days, because cozy.markets' smoothed curves drew prices nobody saw. Picking Trend widens 24 h to a week and shows both lines, because the gap between asks and sales is the point. It's for slow changes like inflation: on the mock Iron Ore it shows sales rising 300 to 350 over 8 weeks. Search and tabs share one slim bar that sticks to the top with the column headers under it (Nov 9). The page scrolls, not a box inside it, because a second scroll area inside the frame breaks the wheel and keys. A new search, tab or sort starts from the top. The usual price is the price alone. Its own Price confidence column next to it (Nov 9) shows a level as three dots and a short label naming what decided it, like `●○○ 1 seller`, `●○○ prices vary` or `●●● sold often`, so the column title and the label explain the dots without a legend or a hover (`usualSource` in `market.js`). It sorts surest first. The item card shows it after the cheapest ask, with the whole reasoning written out, because players rarely hover. The level is 1 to 3 (Thin, Decent, Solid) from plain rules, not a percentage, because there's no true price to measure a percentage against: under 5 named sellers is Thin, only sales by 5 sellers on 2 days make Solid (both 3 until Nov 10), sellers over 2× apart lose a level, and data over a week old or gear with every condition mixed is at most Decent. On the real list (785 items, Nov 9) that was 44 Solid, 198 Decent and 543 Thin, so don't hide Thin by default. The bar's confidence filter is one switch, `Hide ●○○`, at its right end (Nov 9, after poe.ninja's "Show low confidence"): three choices beside the inventory tabs read as more tabs, and sorting by the column already puts ●●● first. It has no count because the tab counts show what it leaves. It starts off and narrows the tab counts. It replaced the word "early" and the "low ask" line, which read like the Cheapest ask column. The list says nothing about each or a set, because players know stars sell as a set (Nov 9). Only the card heading says `Usual price, each` or `Usual price, a set`
- Settings: the Settings tab, saved by `serve.js` in `settings.json` in the app's data folder, because the app's page gets a new port, and so new browser storage, on each start. A new setting goes in `SETTINGS` there with its default. The first is `channelWatch` ("Catch fast channel changes"), on by default. Off, capture drops to 5 frames a second and there's no `watch.js`.
  `textSize` ("Text size", one of `TEXT_SIZES`) zooms the whole page with CSS `zoom`, because sizes are in pixels. The Prices frame zooms with the page, and the popped-out card gets its own zoom, with its window widened to 340 × the size. Zoom also scales `vh` (hence `100vh / var(--zoom)` on the card) and leaves `offsetHeight` unzoomed (hence the multiply in `fitPopOut`). Tested Nov 8 in the browser version and the app's popped-out card. The browser version's pop-out only picks up a new width when reopened.
  `cardHotkey` is saved by the main process instead, and Settings only shows it in the app.
  `autoUpdate` ("Download updates automatically", on by default) is shown on the About tab with the update status, and only in the app. The main process reads it each time an update is found.
  `shareScans` ("Share my scans", on by default) is the upload switch. `cloud.setSharing` applies it at once: off drops scans as they come and any still waiting. The installer asks it on a page of its own (`build/installer.nsh`, the reason the installer is assisted, `oneClick: false`, since Nov 11, always for the current user only), which shows what the app sends and is ticked unless `settings.json` already has it off. NSIS can't merge JSON, so it writes `installer-choice.json` in the data folder, and `takeInstallerChoice` in `serve.js` takes it into the settings at the next start and deletes it. Updates install with `--updated` and skip the page, so they keep the setting. The data folder path is written in `installer.nsh` too, so keep it in step with `desktop/main.js`.
- About tab (`aboutTab` in `index.html`): version, update status with its one button (Check for updates, Download, Restart now, Try again), the `autoUpdate` switch, what the app sends, and every licence and credit. Its links open in the browser (`setWindowOpenHandler` in `desktop/main.js`).
- `theme.css`: the whole look, shared by both pages and the pop-out. Colours and fonts live only in its `:root`. Since Nov 9 a chosen tab or filter is marked by an orange line under it, like the game's inventory tabs (the "Orange underline" theme from `design/themes.html`), not a dark fill. Column headers are muted small capitals, and `--meso-text` orange marks only what the player chose, such as the sorted column, so the prices stay the darkest text
- `fonts/`: Nunito and Fredoka with their OFL licences, bundled because the app works offline
- `design/`: the mockup the look came from. `node design/serve.js` shows it on port 8124. It isn't shipped and `theme.css` is the real source. The mockup opens in the first tooltip-blue colours, and its switch loads `theme-osms.css`, the cream set now in `theme.css`. `compare.html` shows both in photos of the real app. `stall.html` is the stall card redesign, built Nov 8, next to the card before it over a game screenshot. `prices.html` is the Prices page proposal on made-up listings, built Nov 8 (the first round, with two panes and gear grouped by condition, was dropped). `themes.html` (Nov 9) shows the real list in seven colour themes from `themes.js`, switched with the arrow keys, and `node design/check-contrast.js` measures each theme's text colours. `confidence.html` (Nov 9) compared the confidence dots, bars and words on a snapshot of the real list. It needs a server giving `/api/state`, so open it through `serve.js` on a scratch database, not `design/serve.js`. `mock-db.js` (Nov 10) fills a local Worker with a made-up market for designing the Prices item card: one real item per situation (Iron Ore busy for 8 weeks with about 950 listings on round prices rising 15%, Leather flat for 8 weeks, a fast rise, troll asks, one thin ask, sold only, gear in every condition, stars as sets with the scam, a seller relisting lower, sellers 2× apart, 70 listings), printed with what each tests. Scans only happen in made-up play sessions (Nov 10: about 50 over 8 weeks, mostly evenings, a third of days none, one going on now), because real data comes in bursts while the player is in the FM, not spread evenly. A sale is only seen if a later session walks past it. Each item and the sessions have their own seed, and times count back from the run, so rebuild it before comparing. Run `npm run cloud:dev -- --persist-to design/mock/worker` after applying the schema there, then `node design/mock-db.js`, then `CLOUD_URL=http://127.0.0.1:8787 node serve.js` (or the `mock` launch entry, port 8134). It only writes to a local Worker and refuses any other address, so delete `design/mock/worker` to rebuild from nothing
- `test/`: `pricing.test.js`, `market.test.js`, `scanner.test.js` (tooltip cards drawn at known sizes, loading `scanner.js` in Node), plus real game screenshots (`shot*.jpg`, `robe-hover-*.webp` for tall tooltips over chat and shop rows, and `channel-window-2560.webp` and `after-channel-change.webp`, two frames 200 ms apart from a recorded keyboard channel change)

## Things to know

- The stall card must never take focus from the game. It's a `focusable: false` window, and it's dragged by its own pointer code, because a Windows title bar drag (`-webkit-app-region`) activates the window anyway. A real mouse test showed this, so check with real input, not a page script.
- A hotkey (`cardHotkey`, Scroll Lock by default) hides and shows the popped-out card, and pops it out the first time. It's a Windows hotkey (`globalShortcut`), so the game doesn't get that key while the app runs, which is why the player picks it in Settings. `desktop/main.js` registers it and saves it only once Windows gives it the key. The card is hidden, not closed, and comes back with `showInactive()`. Tested Nov 7 with real key events, with focus staying on another app. It wasn't tested with the game itself in front, which runs as administrator. Key events sent from the Bash tool didn't reach Windows, but ones from the PowerShell tool did.
- The channel is only on screen in the Change Channel window, so `channelFollower` in `pricing.js` works it out from that and the loading screen. A click and its confirm can fall between two scans, which used to leave the old channel on every listing until the window was next opened (shops labelled channel 4 at 09:44 were on 12). Scans run on every captured frame (5 a second, the capture's limit) around the window, but a keyboard change takes less than one frame. Two recordings of fast keyboard hops (Nov 7) never once showed the new pick, and one change showed no window at all. So the window followed by a loading screen makes the channel unknown at once, and a loading screen with no window reads the minimap after it, even with no shop open, and makes it unknown if the map is the same. Channels saved before this can be stale. The stall card's bar always shows what's being saved, as `CH.12` or a warning `CH ?`, even when the card is shrunk.
- Every captured frame (30 a second) is also checked for the Change Channel window and loading screens by `watch.js`, a worker with its own copy of the capture, because a keyboard change shows the window for under 200 ms. It looks at a half-size copy shrunk without smoothing on the graphics card: smoothing or a smaller copy melts the gaps between buttons and lost the dark grey one. It takes about 6 ms a frame and watches about 27 frames a second with the game in front. The full scans also read the map whenever it's on show, so it's known before a loading screen. A full scan's map only counts as where a loading screen ended when its frame was taken after it ended: the watch sees the loading screen within a frame, while a slow read of the last frame of the old map was still going, and that late read looked like landing back on the same map, so ordinary map changes lost the channel (Nov 8).
- A capture can freeze around a channel change while the game carries on (`test/change-channel.webp`: the game is on 26 and the card still says 25). The app reconnects by itself after 5 seconds, and only tells the player after 15. A picture that comes back after a freeze can be on another channel, so the channel goes unknown. That picture also shows the card painted at its old height. It didn't happen in a scratch copy with the same content, so it's assumed to be the same stall.
- MapleStory runs as administrator, and MapleScanner captures it fine without that. Once (Nov 7) a running game's window was missing from the window list, and with MapleScanner as administrator capture failed with `NotReadableError: Could not start video source`. The window looked normal from outside, with no capture block set. Restarting the game fixed it, so the picker suggests that when `MapleStory.exe` is running but not listed.
- The stall card's bar sits outside the part that's re-rendered every scan, or a click on its buttons gets lost. `panelTop` and `panelList` are only written when they change, so the list keeps its scroll position.
- Every screen leads with the answer. Players call the public price sites cluttered, and even the clean one hides the price and the cheapest ask. On the stall card each row's answer is one short word (`label` from `verdict`) in a column on the left, and a row gets a second line (`note`) only when there's something to act on. Lines follow the shop's order, not the verdicts, so the card matches what the player sees. The hovered row opens where it is, so nothing moves, and an item that isn't a row (your own) sits in a fixed slot under the list. Between shops it lists the best deals walked past. Popped out, a problem is one short line in the bar, orange for a warning, with the whole text on hover. An opened item in Prices starts with its usual price and the cheapest ask with where it is, then the chart, then asks cheapest first.
- Fonts must keep prices readable at 13 px: an open zero and same-width digits. Atkinson Hyperlegible was tried and its slashed zero turned `9,000` into `9,888`.
- Layout positions in `scanner.js` were measured on a 2000 px wide screenshot and are scaled by button size. The user's game has captured at about 1922 × 1232 and at 2560 × 1440.
- Check reading changes against the real screenshots in `test/`, in a browser page. Native size matters most, because the app captures without resizing. Resized copies are a harsher test than real use.
- The `shot*.jpg` images are blurred by JPEG, but live capture is sharp. A check that passes on them can fail in the game, so also test on a real capture (`test/live-*.png`). One-pixel checks are the usual cause.
- Scan zoom stays at 4×. On real shops 3× and 5× gave wrong prices, which is worse than a misread name.
- Text reading uses Tesseract, bundled from `node_modules` so it works offline. Colour-based checks (sold rows, scroll tiers, the channel grid) were measured on real screenshots, so measure again rather than guess when changing them.
- Hovering equipment you could wear opens a second card, for what you're wearing, to the right. `test/compare-cards*.webp` are real examples, cropped but at native size. Cards are found by the blue dot before their title and the icon panel below it, because a tooltip's blue depends on the background. Only the left card is read. Something blue on a player can pass for a dot (`test/earrings-hover.webp`, a real screenshot with the stall card on top): taken for a compare card, it stretched the title across the shop's white chat box and the title read as `R.A |h`. So the dot inside the tooltip's shape wins, and a compare card's dot must be level with the first. A comparison near the right edge of the screen is untested.
- A hovered item only gets a card when its title is a real item (`tooltipCard` in `app.js`): a misread title (`Meat` read as `Vie at` live, though the screenshot reads fine) or something on the map taken for a tooltip (`gh WA` at the Free Market Entrance, whose portals and chat lines pass for blue dots) gave a card that said nothing true. The raw read still matches the shop row under it.
- The picture's width doesn't give the game's scale: it draws its windows at 1.064 in a 1922 wide window (where `width / 2000` says 0.96) and about 1.27 at 2560 (Cash Shop button 109 → 130 px), and a crop says nothing. A shop's buttons give the scale, and so does a tooltip card: its icon panel is 98.7 px × scale (`PANEL_W` in `scanner.js`, measured against the shop on every test screenshot), so a card works at any size and in a crop (`test/compare-cards.webp` now reads Plunger). A card must be between 0.85 and 1.5, have a dot of 5 to 9.5 × its scale, and agree with an open shop within 12%. Each limit stopped a real false card: a cyan chat line (0.71), the minimap's + button (`test/shot11.jpg`), a 1.27 card beside a 1.0 shop. The scale from the width is still used for a tooltip found only by its blue shape.
- The game moves a tooltip up to fit it on screen, so the row worked out from its position can be wrong (`test/shot7.jpg`). The game draws its own white glove cursor into the picture, over the tooltip when it was moved, so `findCursor` in `scanner.js` looks for it at the tooltip's left edge and its fingertip gives the row. When it's found, the tooltip doesn't count as moved. Before (Nov 9), a shop of six identical Blue Sauna Robes (`test/sauna-six-copies.webp`) only opened its top two rows. Checked on that shop with the tooltip and cursor from `robe-hover-1.webp` pasted in at each row, not yet live. Blurry JPEGs and crops can hide it, and then the rules below apply. A tooltip can also cover its own row's price, so that row isn't read in that frame (`test/live-shop-hover.png`). A row must match the tooltip's name. If it doesn't, and the tooltip is over the shop's list, the only row in the shop with that name is used, and two such rows stay unknown, because one can be a sold copy. A tall tooltip near the bottom of the screen counts as moved, because it may have been, so with two copies in the shop it stays unknown too rather than giving a 30K robe's stats to a 600K one. Its height is worked out from its stat lines, plus room for a description unless OSMS lists the item as gear with none (`tooltipMoved` in `pricing.js`): that room alone made an unmoved Pink-Flowered Earrings above the chat count as moved, so its row never opened (`test/earrings-two-copies.webp`, a 2000 px copy). Scrolling the shop's list moves the row up. A tooltip that isn't over the list is the player's own item (`test/live-inventory-hover.png`) and is never saved to a listing.
- Tooltips are see-through, so a line can go missing, and two reads can miss the same one. Their stat lines are kept by the weakest colour (`TIP_TEXT`), because brightness alone fails over yellow chat and pale shop rows: `test/robe-hover-1.webp` and `-4` read one to three lines that way. Gear stats only count when the item's main lines from OSMS are all there, and again for the item of the line they go on, with no more slots left than it has (`statsFit`, checked on the tooltip, the stall card's line and by the server before saving). There's no upper limit per stat, because what a scroll adds depends on the scroll and a wrong limit would drop heavily scrolled gear. A bonus line with a label that can't be told rejects the whole read, or a misread `LUK` would look like a copy with no LUK. Thin colons get lost (`DEX +1`). Titles end in a gender mark (`Blue Sauna Robe (M)`), which can read as `(Mj` or `[1`, so `knownTitle` drops endings until a real name fits. Colour stats and the orange `(+3)` title read badly (`test/shot6.jpg` reads +2, `test/live-inventory-hover.png` reads `Red lrendo Robe (My`), so how worked an item is comes from the Remaining Enhancements line. Requirement lines can lose their `REQ` to OCR and look like stats, so a bonus only counts with its plus sign. The `(55 +1)` after a value isn't only scrolling: an unscrolled item can show a rolled bonus, so 7 of 7 slots with `(55 +1)` is still clean.
- Throwing stars recharge, so a shop's `500 for 2,222` is one set with 500 left, not 500 stars, and its price is the whole price. `Ilbi, 4 for 600,000` is a known scam that looks like 150K a set. `itemFacts().unitPrice` is the only place a listing's price per item is worked out, from the `recharge` list in `osms-items.json` (OSMS marks those 11 items with a recharge price). Arrows and potions are still priced per item. Icicle, Snowball and Wooden Top are stars too: `800 for 775,000` and `1 for 959,999` are one Icicle each.
- Equipment never stacks, so a gear row is always 1 item (`itemFacts().single`, from the `slots` list). A Reef Claw's `1 for 18,777` read as `11 for 18,777` live, so the amount read on gear is ignored.
- The stall card has one line per row in the shop, in the shop's order with sold rows in place, so line N is always row N and the hovered row is the line that opens. Four identical `Mithril Titans, 1 for 4,399` used to be one line opened whichever was hovered (Nov 8). Identical rows are still saved as one listing with a `copies` count, but each line keeps its own hover stats, and the listing is saved with the first copy's. The list scrolls, so `placeRows` in `pricing.js` lines each frame's visible rows up with the lines already known. A jump of a page or more to rows not read yet matches nothing, so the lines start again from what's on screen, and a line that takes another listing drops its stats: before (Nov 9) a page jump in jackzhou's 12-row shop put three Blue Sauna Robes on the Korean Fan, Heckler and Lionheart lines with their stats, and hovering a robe never replaced them. The scanner gives the cursor's row (`hoverSlot`) even when the tooltip hides that row's price. When the game may have moved the tooltip and there are two copies, no line opens and the item shows under the list. Tested Nov 8 on `test/earrings-hover.webp` with the hovered row copied over the one above, and on `test/shot7.jpg`. Not yet tested live or on a shop that scrolls.
- The game shows the 3% sales fee in every player shop.
- The highest ask the game allows is 499,999,999,999. It changed a typed 999999999999999999 to that (Nov 9). So `parsePlayerPrice` in `scanner.js` treats a bigger number as a misread. A long row ends in `…` (`1 for 499,999,999,999 me...`), and a price that runs into the `…` is cut short and left unknown.
- A shop's title is the panel heading and is saved with each listing, because it's what's written on the stall. It never replaces the seller: titles like `NX` repeat, and prices need to tell sellers apart. A name plate can be hidden by a hat, weapon or effect (`test/shop-covered-name.webp`). Coloured covers are caught and leave the seller unknown, but white, grey or navy ones aren't. A seller or title only counts once it has read the same on two scans.
- Still only tested with recoloured icons: blue (Lesser) and grey (Chaos) scrolls. Rooms above 3 are untested on the expanded minimap.
- The app goes online for three things: the shared price database (`cloud.js`), item icons, and, in the installed app, one update check on GitHub at each start (Nov 10). `serve.js` downloads an icon from OSMS the first time a page shows it, only for ids in `osms-items.json`, and keeps it in `icons/` next to the database, so it works offline after that and OSMS sees one download per item. The saved icons are dropped when `clientBuild` changes. A failed download is an empty slot of the same size, tried again after 10 minutes. `iconTag` in `pricing.js` writes the tag with the whole address, because the popped-out card is an `about:blank` window. A name with two ids (men's and women's) uses the lower one. Tested Nov 8 in the browser version and in the built app's popped-out card.
- **Only the live game window is shared, never a picture** (Nov 10). A screenshot can be edited, so `remember` in `app.js` saves nothing unless live capture is on. The Scanner tab has no paste or drop any more, and its help, "Something not working?" with Save a test frame and Record 30 seconds of frames, and the credit footer were removed at the user's request. To check reading on a screenshot, call `window.app.scanBlob(blob)` from the developer tools: it shows on the stall card and saves nothing. The `test/live-*.png` frames and the Nov 7 to 9 recordings came from those removed tools.
- Tools launched from the Claude desktop app see `%APPDATA%` through a redirected copy, so `%APPDATA%\Maple Scanner` there isn't the user's real data folder. The folder keeps the old spaced name on purpose: the app was renamed MapleScanner on Nov 10, and `desktop/main.js` pins `userData` to the old folder so settings and the install key are found. Don't remove that line. The user's old `prices.db` stays there unused until they import it.
